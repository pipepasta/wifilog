# wifilog 設計書

作成日: 2026-11-08
リポジトリ: `~/ghq/github.com/pipepasta/wifilog`（Rust、`cargo init` 済み）

この文書では、ユーザーが決めたことと、私（設計者）の判断を区別して書く。私の判断には **［設計者判断］** と付ける。

---

## 1. 何を作るか・なぜ

macOS で Wi-Fi の品質を表す各メトリクスを**常駐して記録し続け**、ターミナルの TUI で見るための CLI ツール。

ユーザーがほしいのは、**時刻ごとの各メトリクスの推移**を見ること。見方は2つある。

- **リアルタイム**: 今の状態が数秒ごとに更新されていく画面（watch モード）
- **レポート**: 過去の決まった期間の結果を、同じ見た目の画面で固定表示する

「不安定だった」と自動で判定するのではなく、**推移そのものをグラフで見せる**ことが中心。

## 2. ゴール・非ゴール・アンチゴール

### ゴール
- 電波まわりの値と、ルーター・インターネットまでの遅延を、約5秒ごとに記録し続ける
- `wifilog view` で、全メトリクスの推移をリアルタイムに見られる
- `wifilog show-report --5m|--1h|--24h|--7d` で、過去の期間を同じ見た目で見られる
- 記録は30日分を残す
- 表示する期間の途中でネットワークが変わったら、**ネットワークごとに分けて**見せ、**切り替わった時刻をグラフに印で示す**（ユーザーの判断。§8.1）

### 非ゴール
- SSID の表示（macOS が伏せるため取れない。§4 参照）
- 品質の自動判定やアラート・通知［設計者判断: 要望に含まれていないため］
- スピードテスト（帯域の実測）
- macOS 以外への対応
- 自動起動の仕組みを CLI 自身が持つこと（launchd の仕事。ユーザーの判断）

### アンチゴール（こうなったら失敗）
- sudo や位置情報の許可が必要になる
- 常駐プロセスが CPU やバッテリーを目に見えて食う［設計者判断: 目安として、常駐プロセスの CPU 使用率は平常時 1% 未満］
- 記録が外部に送られる。記録は Mac の中だけに置く
- データ源が取れなくなったとき（Wi-Fi オフ、macOS の仕様変更など）に、黙って何も記録しない。`status` と `view` で「取れていない」ことがわかるようにする［設計者判断］

## 4. データ源（2026-11-08 にこの Mac で確認済み）

### 4.1 電波の値: airportd の LQM ログ
`log stream` で airportd のログを流すと、約5秒ごとに次のような行が出る。

```
[corewifi] LQM: rssi=-40dBm per_ant_rssi=(-39dBm, -40dBm) noise=-95dBm snr=35 cca=11.0% ccaSelfTotal=0 ccaOtherTotal=5 interferenceTotal=5 txRate=866.7Mbps txFrames=29 txFail=0 txRetrans=0 txFallbackRate=520.0Mbps rxRate=866.7Mbps rxFrames=34 rxRetryFrames=0 rxToss=0 beaconRecv=49 beaconSched=49 txFwFrames=21 txFwFail=0 txFwRetrans=0 network = <redacted> bssid = <redacted> channel = 36 BW = 80 band = 2
```

- 取得コマンド: `log stream --predicate 'process == "airportd" AND eventMessage CONTAINS "LQM: rssi="' --style ndjson`
  - 出力は1行1件の JSON。使う項目は `timestamp`（例: `2026-11-08 14:23:08.883962+0900`）と `eventMessage`
  - 先頭に `Filtering the log data using ...` という JSON でない行が出るので飛ばす
- `log show`（過去分の読み出し）ではこの行は残っていなかった。**流れてくるものをその場で拾う**しかない
- 記録する値: `rssi`、`noise`、`snr`、`cca`、`txRate`、`rxRate`、`txFrames`、`txFail`、`txRetrans`、`channel`、`BW`
- `network` と `bssid` は `<redacted>`（伏せ字）で取れない
- このログの書式は非公開で、macOS の更新で変わる可能性がある

### 4.2 遅延: ping
- `/sbin/ping` は sudo なしで使える。ルーター（デフォルトゲートウェイ）へ平均 2.8ms、ロス 0% を確認
- 宛先は2か所［設計者判断］
  - **ルーター**: **Wi-Fi のインターフェースのゲートウェイ**に固定する。既定ルートのゲートウェイは使わない（VPN や有線 LAN が既定ルートになっていると、Wi-Fi のルーターではなくなるため）
    - Wi-Fi のインターフェース名は `networksetup -listallhardwareports` の `Hardware Port: Wi-Fi` の `Device` から取る（この Mac では `en0`）
    - ゲートウェイは `ipconfig getoption <インターフェース> router` で取る（sudo 不要。この Mac で `192.168.11.1` が返ることを確認）
    - Wi-Fi に接続していないときは、ルーター向けの ping を止める
  - **インターネット**: 既定は `1.1.1.1`。`wifilog start --internet <ホスト>` か、環境変数 `WIFILOG_INTERNET` で変えられる（§5）。経路は OS の既定ルートに任せる。VPN 接続中なら VPN を通った遅延になるが、それも「体感するインターネットまでの遅延」として扱う
- 間隔は5秒［設計者判断: 電波の値とそろえる］

### 4.3 どのネットワークにいるか
- SSID・BSSID は `system_profiler`、`ipconfig getsummary` のどちらでも `<redacted>`。`networksetup -getairportnetwork` は「接続していない」と誤った結果を返す
- **ルーターの MAC アドレス**（§4.2 で求めた Wi-Fi 側のゲートウェイに対する `arp -n <ゲートウェイ>`）は取れる。これでネットワークを区別する［設計者判断］
- 画面には MAC アドレスを出す（例: `ルーター aa:bb:…:12`）。名前を付ける機能は v1 では作らない［設計者判断］

## 5. コマンド（ユーザーが決めた形。colima に倣う）

| コマンド | 動き |
|---|---|
| `wifilog start` | 計測プロセスを裏で起動して、すぐにシェルに戻る。すでに動いていたら何もせずその旨を表示 |
| `wifilog start --foreground` | 裏に回らず、その場で計測し続ける。launchd から呼ぶとき用［設計者判断: colima と同じ考え方］ |
| `wifilog stop` | 計測プロセスを止める［設計者判断: start が裏で動く以上、必要］ |
| `wifilog status` | 動いているか、いつから動いているか、最後に記録した時刻（電波と ping それぞれ）を表示［設計者判断］ |
| `wifilog view` | リアルタイムの TUI。計測が止まっていたら `start` してから開く。閉じても計測は続く（ユーザーの判断） |
| `wifilog show-report --5m\|--1h\|--24h\|--7d` | 過去の期間を、`view` と同じ見た目の TUI で固定表示。描画は変わらない（ユーザーの判断） |

- 自動起動は CLI の仕事ではない（ユーザーの判断）。README に launchd の plist の例（`wifilog start --foreground` を `KeepAlive` で動かすもの）を載せる［設計者判断］
- `show-report` の期間フラグは排他。どれも指定しなければ `--1h` とする［設計者判断］
- インターネット向けの ping の宛先の変え方［設計者判断］: `start` のフラグ `--internet <ホスト>`、または環境変数 `WIFILOG_INTERNET`（フラグが優先）。既定は `1.1.1.1`。設定ファイルは v1 では作らない
  - `view` が自動で `start` するときは、環境変数か既定値を使う
  - launchd の plist の例では `ProgramArguments` にフラグを書く

## 6. プロセスの構成［設計者判断］

```
┌────────────────────┐   書く    ┌──────────────────────┐   読む   ┌──────────────┐
│ 計測プロセス         │ ───────▶ │ データディレクトリ      │ ◀─────── │ view /        │
│ (start --foreground) │          │  日ごとの JSONL ファイル │          │ show-report   │
│  ├ log stream の子   │          │  pid ファイル           │          └──────────────┘
│  ├ ping の子 ×2      │          └──────────────────────┘
│  └ ゲートウェイ監視   │
└────────────────────┘
```

- `view` と計測プロセスは**直接通信しない**。計測プロセスがファイルに書き、`view` はそれを読み直す。どちらかが落ちても、もう一方に影響しない
- `wifilog start` は、自分自身を `start --foreground` として子プロセスで起動し、新しいプロセスグループに入れて（端末を閉じても SIGHUP で死なないように）、標準入出力を切り離してから戻る
- 二重起動の防止: データディレクトリの pid ファイルに対して排他ロック（flock）を取る。ロックが取れなければ起動しない。`status` と `stop` は pid ファイルとロックの状態で判断する
- 計測プロセスの中身
  - `log stream` を子プロセスとして起動し、標準出力を1行ずつ読む。子が終了したら数秒待って起動し直す
  - ping はターゲットごとに長時間動く子プロセス（`ping -i 5 <宛先>`）を起動し、出力の各行を読む。`time=... ms` の行を遅延、`Request timeout for icmp_seq N` の行をロスとして記録する
  - Wi-Fi 側のゲートウェイとその MAC アドレスを30秒ごとに確認する。変わっていたら（ネットワークを移った）、ルーター向けの ping を新しい宛先で起動し直し、`net` レコードを1件書く
  - 計測プロセスは「今のネットワーク（ルーターの MAC アドレス）」を持っていて、**すべてのレコードに書き込む**（§7）。どのレコードがどのネットワークのものかを、読み込み時に突き合わせなくて済むようにするため［設計者判断］
  - スリープ中は記録が止まる。それでよい（グラフでは空白として見せる）
- 計測プロセス自身のログ（起動・子プロセスの再起動・エラー）は、データディレクトリの `wifilog.log` に書く

## 7. 保存［設計者判断］

- 場所: `~/Library/Application Support/wifilog/`（`dirs::data_local_dir()`）。環境変数 `WIFILOG_DIR` で上書きできる（テスト用）
- 形式: **日ごとの JSON Lines ファイル**（`samples-2026-11-08.jsonl`）。日付はローカル時刻で区切る
  - 理由: 30日の保存期間を「古いファイルを消すだけ」で実現できる。`tail -f` や `jq` で中身を直接見られる
- 1行1件。種類ごとにタグを付ける。キーは短くしてファイルを小さく保つ

```jsonl
{"t":"2026-11-08T14:23:00.000+09:00","k":"net","net":"aa:bb:cc:dd:ee:12","router_ip":"192.168.11.1"}
{"t":"2026-11-08T14:23:08.883+09:00","k":"lqm","net":"aa:bb:cc:dd:ee:12","rssi":-41,"noise":-95,"snr":34,"cca":18.0,"tx":866.7,"rx":866.7,"txf":29,"fail":0,"retx":0,"ch":36,"bw":80}
{"t":"2026-11-08T14:23:10.012+09:00","k":"ping","net":"aa:bb:cc:dd:ee:12","dst":"router","ms":2.8}
{"t":"2026-11-08T14:23:15.013+09:00","k":"ping","net":"aa:bb:cc:dd:ee:12","dst":"internet","ms":null}
```

  - `ms: null` はロス（タイムアウト）
  - `net` はそのときのネットワーク（ルーターの MAC アドレス）。まだ分からないとき（起動直後や Wi-Fi 未接続）は `null`
  - 計測プロセスは、日ごとのファイルを新しく作ったときにも先頭に `net` レコードを1件書く
- 1日あたりの量の見積もり: LQM 約17,000行と ping 約35,000行で、合わせて数MB。30日で 100〜200MB 程度
- 保存期間: 30日（ユーザーの判断）。計測プロセスが起動時と、日付が変わったときに、30日より古いファイルを消す
- 書き込み途中で止まった最終行など、読めない行は読み込み時に飛ばす

## 8. 画面（`view` と `show-report` で共通。ユーザーが案 A を選んだ）

ブラウザで見せたモックアップのうち、**A: 縦に積む** に決まった。

```
wifilog ─ ルーター aa:bb:…:12 ─ ch36 80MHz ─ 直近15分               14:35:20 ● 計測中
┌ ━ RSSI ━ SNR ────────────────────────────────── -41 dBm / 35 dB ┐
│ （折れ線）                                                        │
├ ━ ルーター ━ インターネット（遅延） ─────── 2.8 / 9.1 ms ・ ロス 0% ┤
│ （折れ線）                                                        │
├ ━ チャンネル混雑度 ─────────────────────────────────────── 18 % ┤
├ ━ 送信速度 ───────────────────────────────────────────── 866 Mbps ┤
├ ━ 再送・失敗 ───────────────────────────────────────────── 0 / 0 ┤
└──────────────────────────────────────────────────────────────────┘
q 終了   ←/→ 時間幅（5分/15分/1時間）   space 一時停止
```

- グラフは横幅いっぱいに縦に5段積む。**全段の時刻の軸をそろえる**ことが最重要（同じ瞬間を縦に見比べるため）
- 段の組み分け［設計者判断］: ①RSSI と SNR、②ルーターとインターネットの遅延（ロス率は見出しに数字で）、③チャンネル混雑度、④送信速度、⑤再送と失敗
- 各段の見出しの右側
  - `view`: 最新の値
  - `show-report`: 期間の平均・最小・最大［設計者判断］
- ヘッダー: ルーターの MAC アドレス、チャンネルと帯域幅、時間幅。`view` は「● 計測中」と現在時刻、`show-report` は期間（例: `11/08 13:35〜14:35`）
  - 計測プロセスが動いていない、またはデータが30秒以上途切れているときは、「● 計測中」の代わりに警告を出す［設計者判断］
- キー操作［設計者判断］: `q`/`Esc`/`Ctrl-C` 終了。`view` のみ `←`/`→` で時間幅を 5分・15分・1時間 で切り替え（既定は15分）、`space` で一時停止
- 記録がない時間（スリープ中など）は線を途切れさせる。ratatui の `Chart` は1つのデータセット内の点を線でつなぐので、**連続した区間ごとに別のデータセットに分けて**描く
- 端末の高さが足りないときは5段を均等に縮める。1段あたり最低3行を下回るなら下の段から省く［設計者判断］

### 8.1 ネットワークの切り替わり（ユーザーの判断: ネットワークごとに分け、切り替わりを印で見せる）

- 表示する期間に含まれるネットワークに、出てきた順に **A, B, C…** と記号を振る
- **グラフ**: データはすべて表示する。ネットワークが切り替わった時刻に、5段すべてを貫く縦の印（点線）を引き、印の上端に切り替わり先の記号を出す。印の位置は全段で同じ（時刻の軸がそろっているため）［設計者判断］
  - 線は切り替わりの前後でつなげない（別の区間として描く）
- **凡例の行**: ヘッダーの下に1行、各ネットワークの記号・MAC アドレス・その期間にいた時間を出す（例: `A aa:bb:…:12 (5時間10分)  B cc:dd:…:34 (2時間05分)`）［設計者判断］
- **見出しの数字**: ネットワークを混ぜた平均は出さない［設計者判断］
  - 期間内のネットワークが1つなら、これまでどおり（`view` は最新値、`show-report` は平均・最小・最大）
  - 複数なら、ネットワークごとの平均を並べる（例: `A 2.8ms / B 14.1ms`）。いた時間が長い順に3つまで出し、残りは「他 N」とまとめる
  - `view` の最新値は、今いるネットワークの値
- ネットワーク不明（`net` が `null`）の区間は、記号 `?` として扱う
- 間引き（下記）では、1つの区間に複数のネットワークが混ざらないように、切り替わりの時刻で区間を切る

### 描画の更新
- `view`: 2秒ごとにファイルを読み直して描き直す［設計者判断］。毎回全件を読み直すのではなく、前回読んだ位置から追記分だけを読む
- `show-report`: 1回読んで描いたら、終了キーを待つだけ。端末のサイズが変わったら描き直す

### 長い期間の間引き［設計者判断］
- `--7d` だと LQM だけで約12万件になる。グラフの横の点数（点字マーカーで「列数×2」）に合わせて時間を区切り、区間ごとにまとめてから描く
  - 折れ線は区間の平均
  - 再送・失敗は区間の合計
  - ロス率は「タイムアウトの数 ÷ ping の数」
  - 見出しの最小・最大は、間引く前の全データから求める

非同期ランタイム（tokio）は使わない［設計者判断］。子プロセスごとにスレッドを1本立てて、チャネルで書き込み担当に渡す。規模が小さく、そのほうが単純。

## 10. 既存の下書きの扱い［設計者判断］

設計前に書いた下書き（`src/lqm.rs`、`store.rs`、`record.rs`、`quality.rs`、`report.rs`）がある。

- `lqm.rs` の解析処理と、実データを使ったテストは流用する（`BW` の追加と、保存形式の短いキーへの対応が必要）
- `quality.rs`（品質の判定）と `report.rs`（不安定区間の文字出力）は、今回の設計にないので捨てる
- `store.rs`、`record.rs` は、日ごとのファイルや ping の追加に合わせて書き直す
- `main.rs` は `cargo init` が作った Hello World のまま
